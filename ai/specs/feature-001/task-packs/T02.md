## Objective
Create a set of golden test fixtures (JSON) for eval — pairs of `{input, evaluation_criteria}` representing real user use cases.

## Scope
- [ ] Create `tests/llm/fixtures/sop_golden_cases.json` with **5 test cases** including:
  - Each case: `id`, `description`, `input` (context dict sent to LLM), `evaluation_criteria` (rubric string for judge)
  - Diverse cases: STEM students, Humanities, MBA, PhD research, career change
- [ ] Create `tests/llm/fixtures/cover_letter_golden.json` with **3 test cases**
- [ ] Create `tests/llm/fixtures/judge_rubric.json` — common rubric for LLM-as-judge:
  ```json
  {
    "sop": {
      "rubric": "Score 1-10: Structure(3pts) + Relevance(3pts) + No-hallucination(2pts) + Tone(2pts)",
      "min_passing_score": 6.0
    },
    "cover_letter": {
      "rubric": "Score 1-10: Opening(2pts) + Fit(3pts) + Specific-examples(3pts) + CTA(2pts)",
      "min_passing_score": 6.0
    }
  }
  ```

### Format of each golden case:
```json
{
  "id": "sop-001",
  "description": "STEM PhD applicant, strong research background",
  "operation": "sop_generate",
  "input": {
    "student_name": "...",
    "target_program": "...",
    "university": "...",
    "degree_level": "phd",
    "field_of_study": "...",
    "research_interests": "...",
    "relevant_experience": "...",
    "academic_achievements": "...",
    "career_goals": "..."
  },
  "evaluation_criteria": "The SOP should mention research background clearly, align with PhD program goals, avoid generic statements"
}
```

## Out of Scope
- Do not call LLM to create fixtures (create manually or use real data)
- Do not create fixtures for checklist or deadline service
- Do not create fixtures for edge cases (error handling) — only happy path

## Acceptance Criteria
- [ ] `tests/llm/fixtures/sop_golden_cases.json` has exactly 5 cases, valid JSON
- [ ] `tests/llm/fixtures/cover_letter_golden.json` has exactly 3 cases, valid JSON
- [ ] `tests/llm/fixtures/judge_rubric.json` has rubric for `sop` and `cover_letter`
- [ ] All `input` fields match the actual service input schema (test using Pydantic validation)
- [ ] The `description` field of each case is clear enough for the reviewer to understand without reading the `input`

## Constraints
- Do not use real PII (use fake names, fake universities if necessary)
- Keep input concise (~200-500 words) to avoid wasting tokens in eval
- Do not modify any files other than `tests/llm/fixtures/`
